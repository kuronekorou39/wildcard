# Wildcard

**自分たちのルールで遊べるポーカークラブを、誰でも作れるように。**
カードの強さや役を定義できるポーカーを土台に、招待・開催・記録の管理まで行えるサービスを目指しています。

**▶ プレビュー: https://kuronekorou39.github.io/wildcard/**

公開中の Pages は、ルール・盤面・進行の挙動を確認するためのプレビューです。
オンラインは一時的な P2P 卓と、Cloudflare で進行・履歴を保存するサーバー卓を選べます。
アカウント・クラブは未実装で、サーバー卓への再接続情報はこのブラウザに保存します。
トップとルール編集は画面内で操作する構成にし、長い一覧だけを内部でスクロールします。
初期チップやブラインドなどは値を押すと編集でき、Enter／フォーカスを外すと確定、Esc で取り消せます。
ルールごとのバナーはルール編集画面で設定でき、このブラウザに保存されます。
ルール選択の検索は初期状態では非表示。「検索・絞り込み」でキーワード・既定／自作、詳細条件で手札枚数・デッキ枚数・ベット形式を指定できます。
サーバー卓は作成キーが必要です。開始ボタン付近の「作成キー」で入力し、参加者はキーなしで招待リンクから参加できます。接続先は配布時の設定で決まり、画面には出しません。
アンティは「アンティ / 人」で設定できます。個別カード枚数とデッキ一覧、CPUの「混在」、卓背景のワイド表示にも対応しています。
ルール編集は右上の「保存」「戻る」で操作し、未保存の変更があれば戻る前に確認します。ストレートの連続は 2…A の本来の順で判定し、ランクの並べ替えは強さだけを変えます。

### 役評価について

エンジンは「フラッシュ」「ストレート」といった概念を一切持たない。役の定義は
すべて `RuleSet` というデータから読む。標準のテキサスホールデムも
`STANDARD_RULESET` というプリセットに過ぎず、以下はすべてデータの差し替えで実現される。

- 役の有効・無効の切り替えと順位の入れ替え
- カードの強さ順の差し替え（A を最弱にする、2 を最強にする）
- スート間の強弱（同ランクのタイブレーク）
- カスタム役の追加（変数ランクで `X, X, Y, Y+1, Y+2` のように条件を書ける）
- 変則デッキ（スートを減らす、ショートデッキ）

### 進行について

`reduce(state, action)` の純粋関数で、通信も時間も乱数も持たない（原則1）。
持ち時間切れは外から渡される `timeout` アクションであり、シャッフルの乱数は
`startHand` に渡す seed または乱数列です。同じ入力からハンドを再現できます。
サーバー版は Web Crypto で作った乱数列を使い、seed や乱数列を参加者へ配信しません。

「誰に何が見えるか」は `project(state, viewerId)` がエンジン側で決める（原則2）。
UI には視点に応じた状態を渡します。ただし、P2P の進行役の端末には全員の手札があり、
この端末からの秘匿を保証するものではありません。

### 遊べるモード

| モード | 現在の進行役 | 状態 |
|---|---|---|
| オンライン対戦 | 部屋を作った人の端末（P2P） | ✅ 一時的な卓で遊べる |
| オンライン・サーバー | Cloudflare Durable Object | 検証用サーバーに接続。主催者の端末に依存しない |
| ソロ（CPU相手） | 同じブラウザ内 | ✅ 遊べる |

どのモードでも、下のルールから選んで遊べる。

#### 現在のオンライン対戦（P2P）

P2P モードは自前のゲームサーバーを使いません。端末どうしが WebRTC で直接つながり、接続のきっかけ
（SDP の交換）だけを公開の WebTorrent トラッカー経由で行う。トラッカーを通るのは
接続情報だけで、ゲームのデータは端末間を直接流れます。GitHub Pages の
URL から利用できますが、接続の成立は外部サービスとネットワーク環境に依存します。
これから作る常設クラブのオンライン基盤とは区別します。

部屋を作った人の端末が進行役（host）になり、そこだけでエンジンが回る。
各 guest には **その人向けに伏せた状態** が宛先指定で送られるので、
他人のホールカードはそもそも手元に届かない。

**進行役は全員の手札を計算できる立場にある。** これは物理のホームゲームで
誰かがシャッフルして配るのと同じ構造で、暗号を使わない限り避けられない。
緩和策として:

- 進行役が誰かを画面に常時表示する
- 部屋を作るとき「自分も席に着く」を外せる。席を持たない進行役の画面には
  誰のホールカードも表示されない。遊ばない人が1人いるなら、その人が
  部屋を作るのが一番安全

**配牌の操作のほうは全員が検証できる。** 配る前に進行役が秘密をコミットし、
全員の乱数を混ぜて配牌を決める。セッション終了後に秘密が公開されると、
配り直しや seed の選び直しがなかったことを各自の端末で確かめられる。
検証が成立するのは、エンジンが乱数を持たず seed を外から受けているから。
仕組みと限界は [docs/fairness.md](./docs/fairness.md) に書いてある。

#### ソロ（CPU相手）

CPU は**役の名前を一切知らない**。カスタムルールの下では「AAは強い」すら前提に
できないので、実際に残りの札を配ってみて勝率を数える（モンテカルロ推定）。
ルールを差し替えても同じコードがそのまま相手になる。

実際、エース最弱のルールにすると AA の推定勝率が下がり、KK が最強のペアになる。
この挙動はテストで固定してある。

#### ルールのプリセット

| ルール | 何が変わるか |
|---|---|
| 標準 | 52枚、手札2枚、よく知られた9種類の役 |
| **オマハ** | **手札4枚。役に使えるのは手札からちょうど2枚と場から3枚** |
| ショートデッキ（6+） | 2〜5を抜いた36枚。フラッシュがフルハウスより強く、最弱のストレートは A-6-7-8-9 |
| **フロップ6枚** | **フロップで6枚開く。場が8枚になる** |
| フラッシュ > フルハウス | 52枚のまま順位だけ入れ替え |
| エースが最弱 | A-2-3-4-5 が普通のストレートに。最強は 9-10-J-Q-K |
| スートに強弱あり | スペード > ハート > ダイヤ > クラブ。チョップが起きない |
| 独自役入り | ミニストレート（3枚連続）とペア＋三連を追加 |
| 素数ストレートあり | 2,3,5,7,J,K だけで5枚揃うと成立する役を追加 |
| ジョーカー1枚 | 53枚。ジョーカーは何にでも化ける。ファイブカードが成立する |
| 2がワイルド | 4枚ある2がすべて何にでも化ける |
| 片目のジャック | スペードとハートのJだけがワイルド。実在のハウスルール |
| カジュアル卓 | 流れた後に続きを見られる（ラビットハント）。手札を1枚見せられる |
| ディーラーが不器用 | ディーラーが札を表にしてしまう。実際の手順どおり回収して引き直し、その札はフロップのバーンに使われる |

**どれもエンジンのコードには一行も手を入れていない。** すべて `Variant` という
データだけで表現されている。

`Variant` は5つの軸（デッキ / 構造 / ベッティング / 役 / 卓の作法）に分かれていて、
手札の枚数、ストリートの数と枚数、バーンカード、使用枚数の制約、
カード単位のデッキ指定（スペードのAを10枚、といった偏った構成）、
ディーラーが札を表にしてしまう確率やラビットハントの可否まで、すべてデータで書ける。

ホールカードは**1枚単位で表にできる**ので、本人が見せた札も、将来のスタッドの
表向きの札も同じ仕組みで扱える。設計と、何をどこまで表せるようにしたかは
[docs/variants.md](./docs/variants.md) にある。

ルール編集は「ルール情報／デッキ／配り方／ベット／役の強さ／卓の作法／受け渡し／検証」を切り替えて操作できます。
自作ルールは保存してそのまま卓で確認でき、JSON で受け渡せます（バナー画像は含みません）。

## 開発

```bash
npm install
npm run dev       # クライアントを起動
npm run dev:server # サーバー版を試す場合、別ターミナルで起動
npm test          # エンジン・クライアント・サーバーの全テスト
npm run typecheck
npm run build     # 静的ビルド（packages/client/dist）
npm run build:server # サーバーのビルド確認（公開はしない）
npm run verify:server # 実通信・再接続・再起動からの復元を確認
npm run bench     # 役評価の速度
```

開発環境は Node.js 22 以上を使用します。

`main` に push すると GitHub Actions が型チェック・テスト・ビルドを通して
GitHub Pages にデプロイする（`.github/workflows/deploy.yml`）。

### 実際に動かして確かめる

テストは「落ちない」ことまでしか見ない。遊べるかと見た目の崩れは実ブラウザで確かめる。

```bash
npx playwright install chromium   # 初回だけ
npm run dev                        # 別のターミナルで

# CPU 相手に1ハンド通して遊ぶ
npm run drive --workspace @wildcard/client

# CPU を相手に遊ぶ
npm run drive:solo --workspace @wildcard/client

# ブラウザ2つを実際に P2P で繋いで遊ぶ（要インターネット）
npm run drive:online --workspace @wildcard/client
```

`WILDCARD_RULE=short-deck` のようにルールを指定して走らせることもできる。
どのスクリプトもショーダウンで「卓の上に同じカードが二度出ていないか」を検査する。

どちらも1ハンド遊びきり、スクリーンショットを残す。
手順の詳細とつまずきどころは `.claude/skills/run-app/SKILL.md` にまとめてある。

## Pages とクラブ版の位置づけ

Pages は、ソロ・オンライン卓でルールと挙動を確認する場所です。
常設クラブでは別途オンラインの基盤を用意し、卓の進行、アカウント、権限、保存と復旧を扱います。
同じゲームエンジンと既存の卓UIを活かしながら、この運営の仕組みを追加します。
最初の完成条件は「開発者が付き添わなくても、クラブを作って遊び、翌週また同じ場所に集まれること」です。
詳細は [開発計画](./docs/roadmap.md) と [アーキテクチャ](./docs/architecture.md) を参照してください。
