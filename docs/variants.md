# バリアントの設計

世の中のポーカーは「少しずつ違うルールの集まり」である。Wildcard の目標は、
それらを**組み合わせて作れる器**を用意すること。この文書は、何を軸として
切り出し、どこまでをデータで表現するかを決める。

## 原則

**エンジンのコードに「ホールデムならこう」という分岐を一切書かない。**

ホールデムもオマハも、ユーザーが作った名前のない変種も、すべて同じ
`Variant` というデータである。エンジンはそれを読んで動くだけで、
特定の遊び方を知らない。これは [architecture.md](./architecture.md) の
原則4 を、役だけでなくゲームの構造まで広げたもの。

## 4つの軸

```ts
interface Variant {
  id: string
  name: string
  description?: string
  deck: DeckRules          // 何で遊ぶか
  structure: HandStructure // どう配って、どう組むか
  betting: BettingRules    // どう賭けるか
  ranking: RankingRules    // 何が強いか
  options?: TableOptions   // 卓の作法
}
```

この軸は互いに独立している。デッキを変えても構造は影響を受けないし、
ベッティングを変えても役の判定は変わらない。だから組み合わせが効く。

### デッキ — 何で遊ぶか

```ts
interface DeckRules {
  suits: Suit[]          // 直積の素になるスート
  ranks: Rank[]          // 使うランク。**弱い順**に並べる
  suitRanking?: Suit[]   // スート間の強さ（強い順）。省略ならスートに強弱なし
  copies?: number        // 直積で作る各カードの枚数（既定1）
  overrides?: { rank: Rank; suit: Suit; count: number }[]  // カード単位の上書き
}
```

直積（スート × ランク × copies）を土台にして、`overrides` でカード単位に
上書きする。この2段構えなら、素直なデッキも極端に偏ったデッキも同じ型で書ける。

| やりたいこと | 書き方 |
|---|---|
| クラブだけ抜く | `suits` から `clubs` を外す |
| 2〜5 を抜く（ショートデッキ） | `ranks` から外す |
| 全部2枚ずつ | `copies: 2` |
| スペードのAを10枚 | `overrides: [{ rank:'A', suit:'spades', count:10 }]` |
| ハートのKだけ抜く | `overrides: [{ rank:'K', suit:'hearts', count:0 }]` |

`overrides` は `suits` に無いスートも足せる（スペードのみ + ハートのA、など）。
ただしランクは `ranks` に含まれていなければならない。強さの順序が決まらないため。

ジョーカーは段階2で入れる（→ ワイルドカード）。

`ranks` の並び順がそのままカードの強さになる。だから「TT が AA より強い」は
並べ替えるだけで実現する。

**ただし副作用がある。** ランクの並び順はストレートの意味も決めるので、
10 を A の上に移すと 9-10-J-Q-K はもう連続ではなくなる。
こういうことが起きるので、編集画面には必ず例示が要る。

### 構造 — どう配って、どう組むか

```ts
interface HandStructure {
  holeCards: number                    // 手札の枚数
  streets: Street[]                    // 場に開く段階
  handSize: number                     // 役を作る枚数（通常5）
  holeUsage?: { min: number; max: number }   // 手札から使う枚数
  boardUsage?: { min: number; max: number }  // 場から使う枚数
}

interface Street {
  name: string
  cards: number   // 開く枚数。0 でもよい（開かずに賭けるだけのラウンド）
  burn?: number   // 開く前に山札から落とす枚数（バーンカード）。既定0
}
```

使用枚数の制約を省略すると「何枚使ってもよい」になる。

| 遊び方 | holeCards | streets（開く/焼く） | holeUsage | boardUsage |
|---|---|---|---|---|
| テキサスホールデム | 2 | 3/1, 1/1, 1/1 | 省略（0〜2） | 省略 |
| オマハ | 4 | 3/1, 1/1, 1/1 | **{2,2}** | **{3,3}** |
| 6枚フロップ | 2 | **6**/1, 1/1, 1/1 | 省略 | 省略 |
| ファイブカードドロー | 5 | なし | {5,5} | {0,0} |

**バーンカードは結果の確率分布を変えないが、必要なデッキ枚数は変える。**
指定できないと「52枚きっかりで回るはず」の計算が狂うので、ルールとして持つ。

**デッキの枚数が足りているか**は `validateVariant` が確かめる。必要枚数は

```
holeCards × 人数 + Σ(各ストリートの 開く枚数 + 焼く枚数)
```

合わせて次も確かめる。

- `holeUsage.max + boardUsage.max >= handSize`（そもそも役を組めるか）
- `holeUsage.max <= holeCards`、`boardUsage.max <= 場の総枚数`
- `overrides` のランクが `ranks` に含まれているか

### ベッティング — どう賭けるか

```ts
interface BettingRules {
  limit: 'no-limit' | 'pot-limit' | 'fixed-limit'
  straddle?: { max: number }              // ストラドルの重ね回数
  streetCaps?: { street: number; noAllIn?: boolean; maxTotal?: number }[]
  maxRaisesPerRound?: number
}
```

**掛け金（SB/BB/アンティ）はここに入れない。** 「NLホールデム $1/$2」の
$1/$2 は遊び方ではなく卓の設定で、同じバリアントのまま変えられる必要がある。
額は `GameState` 側に置く。ここに入れるのは制度だけ。

`streetCaps` の `street` は `-1` がプリフロップ、`0` 以降が `streets` の index。
「プリフロップでオールイン禁止」は `{ street: -1, noAllIn: true }`。

**この軸は役の判定と完全に独立している。** 後から足しても何も壊れないので、
実装の順番は最後でよい。

### 役 — 何が強いか

```ts
interface RankingRules {
  hands: HandRanking[]   // 強い順
  wilds?: WildRule[]     // ワイルドカードの扱い
}
```

`HandRanking` の中身（`HandPattern`）は既存のものを引き継ぐ。
カードごとの条件と、手全体に課す条件の組み合わせ。

#### ランク条件の表現

```ts
type RankSpec =
  | { type: 'fixed'; value: Rank }                      // 特定のランク
  | { type: 'oneOf'; values: Rank[] }                   // いずれか
  | { type: 'variable'; name: string; offset?: number } // 変数。X, X+1 ...
  | { type: 'any' }
```

`oneOf` があると「素数ストレート（2,3,5,7,J,K のいずれか5枚）」のような役が
書ける。`variable` は同名なら同ランクを指し、異なる名前は異なるランクを指す。

#### ジョーカーとワイルドカード

```ts
interface WildRule {
  cards:
    | { kind: 'joker' }                      // ジョーカー
    | { kind: 'rank'; ranks: Rank[] }        // 「2がワイルド」
    | { kind: 'card'; cards: {rank, suit}[] } // 「片目のジャック」
  becomes?: { ranks?: Rank[]; suits?: Suit[] }  // 省略なら何にでも
}
```

ジョーカーも「2がワイルド」も「片目のジャック」も同じ仕組みで表す。
ジョーカーの枚数は `deck.jokers`。

ジョーカーの `rank` と `suit` には意味がない（置き換え前の仮の値）。
同一性の比較には必ず `cardKey()` を使う。`${rank}${suit}` で比べると
実在のカードと衝突する。

**ワイルドを入れるならファイブカードを役に足す必要がある。** 同じランク5枚が
成立するようになるため。プリセットでは最強の役として置いてある。

#### 置き換えの候補をどう絞るか

素朴に「ワイルド1枚につきデッキの全種類」で総当たりすると、実測で
1枚25ms・2枚472ms・**3枚5.3秒** かかって使い物にならなかった
（C(7,5)=21 通りの組み合わせそれぞれで展開するため）。

**役のパターンを見れば、その役に要る候補はごく少ない。**

- スートの条件が無い役（フォーカード、ストレート等）では、スートは結果に
  影響しない。1つに固定してよい
- 同一スート条件の役（フラッシュ等）では、**ワイルドは全員同じスートになる**。
  1枚ずつ独立に選ばせる必要がない
- ランクは固定指定なら1つ、`oneOf` ならその一覧だけ

これで 1枚6.9ms・2枚26ms・3枚67ms まで落ちた（18〜79倍）。

正しさは **differential テスト** で担保している。素朴な総当たりを
`allSubstitutions` として残してあり、ランダムな手で両者の結果が
一致することを確かめる。速くするために正しさを捨てていないことを、
主張ではなく動くもので示すため。

### 卓の作法 — 勝敗には関わらないが場を左右するもの

```ts
interface TableOptions {
  exposedCardChance?: number          // 札を1枚表にしてしまう確率（ミスディールではない）
  misdealChance?: number              // 2枚以上表にして配り直しになる確率
  rabbitHunt?: boolean                // 流れた後、配られるはずだった札を見せる
  showCards?: 'none' | 'one' | 'any'  // 自分の手札を見せられるか
  runItTwice?: { max: number }        // オールイン決着で複数回配る（未実装）
}
```

役の強さにも配り方にも関わらないが、卓の空気を決めるもの。
どれも既定では無効で、明示的に有効にしたときだけ動く。

#### ホールカードは1枚単位で表にできる

手札を見せる操作と、将来のスタッド（表向きの手札）は、同じ仕組みで済む。

```ts
interface Player {
  holeCards: readonly Card[]
  exposedHoleCards: readonly number[]  // 表になっている札の位置
}
```

`project` はこの位置だけを見て、見せてよい札を決める。だから

- 本人が1枚だけ見せた
- スタッドで何枚かが最初から表向き

が同じ経路で扱える。**以前「保留」としたスタッドへの道もこれで開く**
（残るのは「どの札を最初から表にするか」を構造側で決める部分だけ）。

**ディーラーの露出はここには入らない。** 回収して引き直すので手札は割れず、
公開されるのは「誰の手にもない死んだ札」のほうだから（`GameState.exposedCards`）。

#### ディーラーが札を表にしてしまったとき

実際のポーカー（Robert's Rules / TDA）では2通りに分かれる。**この違いは大きい。**

| 枚数 | 扱い | 手札は割れるか |
|---|---|---|
| 1枚 | **ミスディールではない。** 回収して山札の top から引き直し、その札はフロップのバーンに使う。手は通常どおり続行 | **割れない** |
| 2枚以上 | **ミスディール。** 手札を回収して最初から配り直す | — |

1枚の場合に全員が知るのは「その札はもう出ない」という情報だけで、
本人の手札が公開されるわけではない。

#### なぜ「露出した札をバーンにする」のか

山札を `c1 … cN`（手札）, `c_{N+1}`, `c_{N+2} c_{N+3} c_{N+4}` と置くと:

| | 手札 | バーン | フロップ |
|---|---|---|---|
| 通常 | c1…cN | **c_{N+1}** | c_{N+2} c_{N+3} c_{N+4} |
| 露出（ck が表に） | c1…cN から ck を抜き **c_{N+1}** を補充 | **ck** | c_{N+2} c_{N+3} c_{N+4} |

**フロップに出る札が変わらない。** 引き直しに使う「山札の top」は本来バーンに
なるはずだった札なので、露出した札がその席に収まる。つまりこの手順は
**ディーラーのミスで場が変わってしまうのを防ぐ**ために組まれている。
別途焼くと場がずれる。

この性質はテストで固定してある（露出の有無でコミュニティカードが一致する）。

ハウスによっては別途焼く運用もありうるので、`exposedCardBecomesBurn` で
選べるようにした（既定 true）。false にすると場がずれ、1ハンドで消える枚数も
1枚増えるので、デッキの必要枚数もそのぶん多く見込む。

**乱数はすべて seed から導く。** そうしないと配牌の検証
（[fairness.md](./fairness.md)）が壊れる。同じ seed からは同じ結果が
再現される（配り直しも含めて）。

ただし **使う人には不具合に見えるおそれがある。** 既定は無効にし、
起きたときは画面に「何が起きて、どう処理したか」を明示する。

#### ランイットトゥワイス（未実装）

オールインで決着したあと、残りのボードを複数回配ってポットを分ける。
これだけは状態の形が変わる——ボードが1本ではなくなるので、
`communityCards` を複数本持つ形に作り直す必要がある。他と混ぜず別に扱う。

### 段階4で分かったこと — 例の「正しさ」と「読みやすさ」は別物

例の生成は、**候補を作って既存の `evaluateExact` に聞く**形にした。
生成側に成立判定を持たせないので、判定と二重管理にならない。
旧 `HouseRulesPage.tsx`（3,651行・未完）が崩れたのはここだった。

正しいだけでは使えない、というのが分かったのはブラウザで見てからだった。

| 症状 | 原因 | 対処 |
|---|---|---|
| フォーカードなのに札が3枚しか揃って見えない | スートの抽選が重なって実札が取れず、ワイルドで代用していた | 条件を満たす札を1つに決め打ちせず、空いているものを順に試してから代用する |
| ファイブカードが作れない | 同じランクは4枚しかない | **ワイルドが無いと成立しない役がある**。実札が尽きたらデッキのワイルドを使う |
| `JOKER→8♠` と出るのに手の中に本物の 8♠ が居る | フォーカードではスートに意味が無く、便宜上決めたスートを表示していた | `patternUsesSuits` を見て、意味が無ければランクだけ出す |
| 素数ストレートの例が `2♥ J♣ K♣ 5♣ 3♥` で読めない | 生成順のまま出していた | **同じ条件が続く区間の中だけ**で並べ替える。フルハウスの「3枚組→2枚組」という並び自体が説明なので、ランクで一律に並べ替えてはいけない |
| ストレートの例がクラブ4枚でフラッシュに見える | スートを無作為に選んでいた | スートが結果に関わらない役（`patternUsesSuits` が false）でだけ散らす。「同じスートが3枚以上」のような役で散らすと成立しなくなる |
| ハイカードの例が `7♥ 2♠ 3♠ 4♠ 10♠` | キッカーの候補を最初に一度だけ並べていた | 1枚引くごとに選び直す |

### 段階5で決めたこと — 編集画面

**編集中の値は Variant そのもの。** 画面用の中間表現を持たない。
旧 `HouseRulesPage.tsx` が 3,651行で力尽きたのは、画面の状態とルールの表現が
別物で、相互変換を書き続けたためだった。

例外が1つある。役の条件だけは「まとまり」を挟む（`rules/blocks.ts`）。
`HandPattern` はカード1枚ずつの条件が並んだ配列で、判定にはこの形がよいが、
人は1枚ずつ考えない——フルハウスは `X X X Y Y` ではなく「3枚組と2枚組」である。
変数名（X, Y）は blocks が振るので、画面には出てこない。

**戻せない形は編集させない。** 1枚ずつスートを指定した役のように、まとまりで
表せない条件は作れてしまう。黙って近い形に直すと、編集画面を開いて閉じただけで
役が変わる。`toBlocks` が null を返したら、その役は読み取り専用にする。
プリセット全部の役が往復できることをテストで固定してある。

#### 保存と受け渡し

保存先はこの端末の localStorage しかない（サーバーを持たない）。
**保存したデータは「外から来た JSON」として扱う**——前のバージョンで保存したもの、
手で書き換えられたもの、容量超過で途中まで書かれたものが来る。
読むときは必ず `parseVariant` を通し、1つ壊れていても他のルールは失わない。

取り込みでは **id を必ず振り直す**。そうしないと、他人のルールが `standard` を
名乗ってプリセットを上書きできてしまう。

id の採番は時刻＋乱数では足りなかった（テストで衝突が出た）。通し番号を混ぜて、
同じセッションでは必ず別の id になるようにしてある。

#### 編集画面が教えてくれること

作ってみて分かったのは、**例示がそのまま検算になる**ことだった。

- クラブを抜く（3スート）と、フォーカードの例が「このデッキでは成立しない」になる。
  同じランクが3枚しかないので当然だが、言われるまで気づかない
- 足したばかりの役は、いちばん下にあるうちは例が出ない。上の役に先に当たるため。
  強さを上げると例が出る——**役の強さの意味がそのまま見える**

### 段階6で決めたこと — ランイットトゥワイス

オールインで決着するとき、残りの札を複数回走らせてポットを分ける。
勝ち負けの分散が下がるので、大きなポットほど持ちかけられる。

**ボードの持ち方**: `communityCards` は1本目のままにして、2本目以降を
`extraBoards` に持つ。読むときは `boardsOf(state)` が
`[1本目, 2本目, ...]` を返すので、**「1本目か2本目か」で場合分けしない**。
1本しか走らないのが普通なので、`communityCards` の意味を変えずに済ませた。

**聞く場面**: これ以上ベッティングが無く、まだ開く札が残っているとき。
`advanceStreet` が残りを一気に開きに行く手前がちょうどその場面なので、
そこで止めて `phase: 'runChoice'` にする。聞き終われば残りを一気に開くので、
「もう聞いたか」を覚えておく必要がない。

**全員の同意が要る**（1人でも断れば1本）。実際の卓の作法どおりで、
「2人のうち1人が嫌がったのに2本走った」が起きない。
時間切れは「断った」こととして扱う——返事が無いまま走らせると、
同意していない人の金が動く。

**ポットの分け方**: 各層を本数で等分し、1本ごとに勝者へ配る。
割り切れない端数は先の走りから1枚ずつ乗せるので、合計は必ず元の額に戻る。
1本なら今までと同じ結果になるため、走りの数で呼び分ける分岐が要らない。

**デッキ枚数**: 本数ぶん余分に要る（プリフロップで全員オールインが最悪）。
`extraCardsFor` に入れたので、始める前の検算でも編集画面の「最大◯人」でも
同じ数字になる。ここが食い違うと「10人まで」と出したのに弾かれることになる。

段階1で遊べるようになったもの: オマハ（手札4枚・ちょうど2枚使用）、
フロップ6枚、カードを開かないベッティングラウンド、場の無いバリアント、
スペードのAを10枚のような偏ったデッキ、素数ストレートのような `oneOf` の役。

段階1が終わった時点で**オマハが実際に遊べる**ようにする。
書いただけで動かない設計を残さないため、各段階は遊べる形で区切る。

## 決めたこと・決めていないこと

決めたこと:

- 4つの軸は独立させる。組み合わせが効くのはこれが理由
- ランクの強さは `ranks` の並び順ひとつで表す。別の強さ表を持たない
- ストリートは名前と枚数の配列。フェーズ名をエンジンに焼き込まない
- ワイルドは置換の総当たりではなく、条件側で吸収する

決めていないこと:
