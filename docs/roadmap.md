# Wildcard — 開発計画

2026-10-30 更新。製品の目標と運営方針は [concept.md](./concept.md) を参照。
このリポジトリは GitHub Pages の検証版として仕上げ、区切りのタグを基に別リポジトリで AWS ベースのサービスを開発する。
現在は Cloudflare に検証用サーバーがあるが、AWSへの移行、新リポジトリ、タグ、クラブ機能はいずれも未着手。
当日の7項目を改修し、全員アンティ、個別カード編集、CPU混在、退出・期限表示などを検証済み。結果と持ち越しは課題メモに記録する。

## このリポジトリの区切り

**ゲームとルール編集を GitHub Pages で安定して検証でき、AWS版が挙動を比較できる基準を残す。**

トップからルール編集・保存・対局・結果・退出までを仕上げる。
スマホ縦横とPC、2・6・10人、代表的なカスタムルール、掛け金とチップ分配を確認する。
検証サーバーが使えなくてもソロ・ルール編集・表示確認が動く状態を保つ。
退出の説明と実動作を一致させ、既知の制限を記録する。

タグ候補は `v0.1.0-preview`。修正後のテスト・型チェック・ビルド・ブラウザ確認と Pages の公開版を確認してから付ける。
具体的なチェックリストと新しい課題の現状・対応案は [preview-release-checklist.md](./preview-release-checklist.md) を唯一の作業一覧とする。

### 仕上げの課題と対応状況

| 対象 | 今回の対応 |
|---|---|
| ソロ退出・部屋の寿命 | 終了と退出の文言を分離。状態・保存期限、期限切れ参加情報の整理を追加 |
| 個別カード枚数・デッキ一覧 | 個別編集、一覧・重ね・扇形表示を追加。重複札のCPU計算・使用札表示を修正 |
| アンティ | 全員アンティを全モードに追加。中央への徴収、履歴、少額スタックを検証 |
| レイズ候補 | BB規模で比率候補を丸める。正確な最小／最大と手動1チップ調整を維持 |
| 卓の背景 | 席等の配置を維持して、背景だけ広げるワイド／標準切替を追加 |
| CPUのスタイル | 卓の開始時に固定する「混在」を追加。従来の全員共通設定も維持 |

これらは実装・ローカル検証済み。タグ前に公開版・代表ルール・既知の制限を最終確認する。
ソロの中断・再開、BBアンティ、部屋の保存方針変更などは仕様選択が必要。

## 新しい AWS プロジェクトの最初の完成条件

**開発者が付き添わなくても、クラブを作って遊び、翌週また同じ場所に集まれる。**

登録 → クラブ作成 → ルール設定 → 招待 → 開催 → 記録の確認までがつながり、
主催者の端末やその場限りの接続に依存せず、メンバーと記録が残る状態を目指す。

タグからエンジン・卓UI・素材・テスト・Git履歴を引き継ぎ、AWSで1卓を成立させてからアカウント・クラブをつなげる。
サービスの具体的な構成・認証方式と、新リポジトリの名前・公開範囲は別途決める。
新プロジェクトを主な開発先とし、Pages版は検証用に維持する。

## 現在の土台

- ゲームエンジンは通信・時刻取得から分離され、ルール定義をデータとして受け取る。
- ソロ、ホットシート、一時的な P2P 対戦が動く。
- ゲーム画面、ルール編集、ブラウザ内のルール保存と JSON の受け渡しがある。
- アクション、盤面、チップの動きを確認する結果表示があり、サーバー版では直近100ハンドを保存・再表示できる。
- サーバーが進行する10人卓、再接続、期限の保存、操作の重複排除を実装した。
- アカウント、継続するクラブ、クラブのチップ台帳はこれから作る。

Pages は引き続きルールと表示の確認に使う。
クラブ対応に必要な修正を除き、ゲーム画面の全面的な作り直しは開発の前提にしない。

## 既存サーバー試作 — AWS 版へ引き継ぐ検証項目

以下は Cloudflare で作った試作の範囲と検証項目。未検証の事項を含む。
Cloudflare の本番運用・請求検証の完了は、Pages検証版のタグ条件にしない。
AWS 版ではこの要件を使い、クラブ機能を広げる前に10人卓・復旧・費用を検証する。

### 試作の実装範囲

- 既存エンジンを動かすサーバー側の卓と、現在の画面につなぐ通信層。
- 接続者の識別、席への操作権限、視点ごとの状態配信。名前や送信された `playerId` だけで本人と判断しない。
- 手番、期限、自動進行の管理。接続の有無にかかわらず時刻を判定する。
- 状態・期限の保存と再読込。再接続時は最新の状態を受け取る。
- 操作の識別と重複排除。遅れて届いた操作や再送で二度チップが動かないようにする。
- ハンドの結果と手順の保存。閲覧用の記録に非公開の手札や配牌を復元できる情報を混ぜない。
- 使用量、エラー、保存量を記録し、運営費を計算するための計測。

### 検証項目（未完了の項目を含む）

- 最大10人でハンドを最後まで進め、通常のベット、サイドポット、同点分配、オールイン時のランアウトを確認できる。
- 主催者がブラウザを閉じても卓が維持され、参加者は再接続して自分の席に戻れる。
- 処理の再起動を挟んでも、確定済みの操作・結果が失われず、期限切れや精算が二重に実行されない。
- 他人の席への操作、古い手番への操作、同じ操作の再送を適切に扱える。
- 参加者・観戦者ごとの表示と通信内容を確認し、未公開カードやシャッフル情報を配信しない。
- ハンド終了後に保存した結果・盤面・操作順・チップの動きを再表示できる。
- 10人卓を1時間動かし、稼働中と待機中の使用量を分けて測る。複数卓についても追加で測り、想定する月間利用量で試算する。

最初の検証先は Cloudflare Workers + SQLite Durable Objects とした。
ローカルで10人卓2つ＋待機卓1つを1時間運転し、チップの総量を保持した。
実装・公開手順は [server-preview.md](./server-preview.md)、測定値と月間利用量の仮定は [server-measurement.md](./server-measurement.md) に記録する。
公開環境での更新・障害後の復旧確認と、継続運転の課金量測定は未実施。ローカルの検証を実課金の検証済みとして扱わない。
この記録を比較基準にし、運用するAWS構成で改めて費用を測る。
1卓の測定だけから無制限のクラブ運営を見積もらない。
CPU 相手の負荷は人間の10人卓と分けて測り、初期のオンライン版に CPU を含めるかは別途判断する。

## AWS 版 — 最小限のクラブを一通り使える状態にする

| 範囲 | 完了条件 |
|---|---|
| アカウント | 登録・ログイン・再ログインができ、メンバーとして同じクラブに戻れる |
| クラブ | 名前・アイコン・バナーを設定でき、一人が複数クラブに所属できる |
| メンバー | 管理者と一般メンバーの権限を分け、参加・招待・参加権限の取り消しを管理できる |
| 招待 | リンクから所属するクラブを確認して参加でき、招待リンクを無効化できる |
| ルール | クラブに保存し、選んだルールで卓を開ける。後から編集しても進行中の卓や過去の記録のルールは変わらない |
| テーブル | 管理者が開催・終了でき、メンバーが参加・再接続できる。初期公開時の同時卓数は運営予算に合わせて制限する |
| チップ | 付与・持ち込み・精算などの増減を記録でき、同じ処理を繰り返しても二重計上しない |
| 記録 | 開催とハンドの結果を後から開ける。公開範囲は所属・権限・カードの公開状態に従う |

スマホと大画面の両方で、登録から結果の確認まで通して確かめる。
別のクラブの情報や権限が混ざらないことも確認する。

### この段階の実装前に決める仕様

- チップを開催ごとにリセットするか、クラブで持ち越すか。付与できる人、持ち込みと精算の時点。
- 招待から参加までの手順と承認の有無。ゲスト参加を含めるか。
- 保存したルールの編集権限と、個人のルールをクラブへ取り込む手順。
- 履歴の閲覧者、保存期間、退会後の扱い。
- 認証サービスとアカウント復旧の方法。

未確定の仕様をすべて選択式にして、初期版の設定を増やすことは避ける。

## AWS 版 — 少数クラブで継続利用を確認する

まずは招待した少数のクラブで、複数回の開催を試す。

- 主催者が説明なしで作成・招待・開催・記録確認を行えるかを見る。
- 翌週も同じクラブで開催できるか、止まった場面や問い合わせを記録する。
- 月間の実費と、保守・問い合わせに使った時間を確認する。
- 保存データのバックアップと復元を確かめる。
- 続けて使う価値がある機能と、主催者が料金を払いたい範囲を確認する。

この結果から、公開範囲、同時卓数、保存期間、有料プランの必要性を判断する。
クラブ検索、募集機能、イベント管理、設置版は、その後の候補とする。

## 費用の考え方

収益化前の予算は月数千円、設計上の仮の目安は月3,000円程度。
特定サービスの基本料金だけで全体の運営費を判断しない。

| 計測・確認するもの | 使い道 |
|---|---|
| 同時卓数、卓の稼働時間、操作・通信量 | 卓の処理と配信にかかる費用を見積もる |
| 状態・履歴の保存量と読み書き | 継続するクラブと履歴の費用を見積もる |
| バナー等の画像、認証、メール、ログ、バックアップ | 卓以外で発生する費用を含める |
| 月間請求額、問い合わせ、復旧作業 | 金額と作業時間の両方で継続性を判断する |

使用量の通知に加え、新規卓の作成数、画像容量、履歴の保存期間などを制限する設計にする。
通知だけでは請求の上限にはならない。制限は既存の対局の精算やデータ保全を妨げない形にする。
利用規模を広げる際は、その時点の実測値と予算を見直す。
