# Wildcard — アーキテクチャ

旧3プロジェクトが合流できなかった原因はただ一つ、**ゲームロジックが通信層と絡まっていたこと**である。
`poker-web-test` の `PokerGame.ts` は socket 配信とコールバックに依存し、
`game-ui` の `server.js` は Express のハンドラ内にロジックが直書きされていた。
結果として「片方のUI + 片方のエンジン」という当然やりたかった組み替えができなかった。

Wildcard はこの一点を設計で封じる。

現在はブラウザ内での進行と一時的な P2P 対戦を実装している。
同じエンジンと卓UIを活かしたサーバー版を追加し、ローカルと Cloudflare の検証環境で確認している。
製品の範囲は [concept.md](./concept.md)、開発順序と完了条件は [roadmap.md](./roadmap.md) を参照。
以下では実装済みの構成と、クラブ版で追加する構成を区別する。

## 原則1 — エンジンは純粋関数である

```
reduce(state, action) -> state
```

エンジンは通信・時間・乱数の副作用を持たない。

- **通信を持たない**: socket も HTTP も知らない
- **時間を持たない**: 持ち時間切れは外から `{type:'timeout'}` という action として入る
- **乱数を外から受ける**: seed または乱数列を引数で受ける。サーバー版は Web Crypto の乱数列を使い、エンジン内で棄却法により偏りなく添字へ変換する。

## 原則2 — 秘匿はエンジンの責務である

```
project(state, viewerId) -> VisibleState
```

「誰に何が見えるか」をUIや通信層の判断に任せない。エンジンが視点ごとに state を伏せて返す。
自分のホールカードだけが見え、ショーダウンで初めて他人の札が開く。

ソロとホットシートでは、`project` の結果をUIに渡して画面への表示を制御する。
P2P では host が guest の視点ごとに投影して配信するが、host 自身の端末には全状態がある。
`project` は全状態を持つ端末からの秘匿を保証するものではない。

クラブ版ではサーバーが認証済みの接続者と所属・席を確認して `viewerId` を決める。
クライアントが指定した視点をそのまま信用しない。通信、保存履歴、ログの公開範囲にも同じ区別が必要になる。

## 原則3 — UI と進行役を Transport で分離する

クライアントはエンジンを直接叩かず、`Transport` 越しに叩く。

| 構成 | 進行役 | 状態 |
|---|---|---|
| `LocalTransport` | 同じブラウザ内のエンジン | ソロ・ホットシートで実装済み |
| `HostTransport` / `GuestTransport` | host のブラウザ内のエンジン。WebRTC で接続 | 一時的な P2P 卓で実装済み |
| `ServerTransport` | サーバー側のエンジン。WebSocket で接続 | 席の復元・同一操作の再送・保存済み状態の受信を実装済み |

`Transport` は現在 `snapshot` / `subscribe` / `dispatch` を公開し、UIは `TableSnapshot` を受け取る。
サーバー接続もこの境界を使用する。送信待ちと受領結果を保持し、再接続では保存済みの状態を優先する。

**ゲームエンジンと卓UIを再利用することと、クラブのオンライン基盤を作ることは別の作業である。**
通信の差し替えに加え、本人確認、権限、永続化、復旧、チップの台帳を実装する必要がある。

## 原則4 — ルールは設定データである

遊び方をハードコードしない。`Variant` というデータを受け取って動く。

```
evaluate(hole, board, variant) -> HandResult
reduce(state, action)           // ストリートも手札の枚数も variant から読む
```

役の強さだけでなく、デッキの中身・手札の枚数・場の開き方・使用枚数の制約まで、
すべて `Variant` に入っている。標準のテキサスホールデムもオマハも、その一例に
すぎない。つまり「カスタムルール対応」は後付け機能ではなく、最初から唯一の経路。

5つの軸（デッキ / 構造 / ベッティング / 役 / 卓の作法）への分け方と、何をどこまで
データで表せるようにしたかは [variants.md](./variants.md) にある。

クラブ版では保存したルールと、実際に卓で使ったルールを区別する。
開催時の定義を保存し、編集によって進行中のゲームや過去の記録の意味が変わらないようにする。

## サーバー版とクラブ版の責務

### 卓の進行と復旧

サーバーが操作を受け取り、本人・席・手番・期限を確認してエンジンに渡す。
卓ごとの更新を順序付け、操作の識別子と確定した状態を保存してから結果を返す。
再送・再起動・期限処理によって、同じ操作や精算が二度適用されないようにする。

`packages/table` の `TableRuntime` はブラウザ内のタイマー方式と、保存状態・時刻を渡す方式を持つ。
`packages/server` は1卓を1つの Durable Object として処理する。
状態・操作の受領結果・履歴・次の期限を同じストレージトランザクションで保存した後、視点別に配信する。
期限は Durable Object の alarm で起こし、再起動後も保存した期限から判定する。
配牌・チップ移動などの描画と音はブラウザに残し、ゲーム進行の確定と表示を分ける。

サーバー版の配牌は Web Crypto の乱数列を使用する。P2P の seed 検証プロトコルとは独立している。
内部には山札・未公開カードを含む状態を保存するが、配信と履歴閲覧には必ず `project` を適用する。
配牌の公正さを参加者が暗号学的に検証できる機能は、サーバー版にはまだない。
現在の本人識別はランダムな接続資格のハッシュと席の対応で、アカウント・所属の確認は未実装。

### クラブの管理と保存（未実装）

- 共通アカウントと、クラブごとの所属・管理権限。
- クラブの外観、招待、保存したルール。
- 卓の状態、開催とハンドの記録、その閲覧権限。
- クラブのチップ付与・持ち込み・精算の台帳。卓の終了と精算が途切れても復旧できる仕組み。

チップの持ち越し方針などの未確定事項は [開発計画](./roadmap.md) に集める。
これらのデータと権限の責務は、純粋なゲームエンジンに混ぜない。

### 小規模から運営するための構成

複数クラブが共通の基盤を利用し、所属・データ・操作権限をクラブ単位で分ける。
クラブの保存と卓を処理する時間を分けて扱い、待機中の計算量を抑える。
同時卓数、保存量、処理量を測り、月数千円程度の予算に合う運営範囲を判断する。

卓の検証環境は Workers + SQLite Durable Objects を採用した。クラブのデータ基盤と認証方式は未選定。
特定のクラウドの無料枠や価格をアーキテクチャの恒久的な前提にしない。

## ディレクトリ構成

```
wildcard/
├── docs/
│   ├── concept.md          製品の目標・用途・運営方針
│   ├── roadmap.md          開発順序・完成条件・予算
│   └── architecture.md     本ファイル
└── packages/
    ├── engine/             純粋TS。依存ゼロ。ここが資産の本体
    │   ├── src/
    │   │   ├── types.ts    ドメイン型とルール定義モデル
    │   │   ├── deck.ts     デッキ生成・シャッフル（seed式）
    │   │   ├── rules/      役評価（Variant を解釈する）
    │   │   └── game/       進行・ポット・履歴・視点投影（project.ts）
    │   └── test/
    ├── table/              卓の時刻・演出・通信形式を共有
    ├── server/             Workers + SQLite Durable Objects。進行・保存・復旧
    └── client/             React + Vite。Pages のプレビューと各 Transport
```

サーバーの動かし方と検証範囲は [server-preview.md](./server-preview.md) を参照。

`engine` が依存ゼロであることは意図的な制約である。これが守られている限り、
エンジンはブラウザでもNodeでもCLIでもテストランナー内でも同じように動く。
