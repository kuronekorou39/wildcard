# Wildcard — コンセプト

## 一言で

**身内のホームゲームのための、ルールを自分で定義できるポーカー。**

## なぜ作るのか

既存のオンラインポーカーは「公式ルールで、見知らぬ相手と、リアルマネーに近い緊張感で」遊ぶために作られている。
欲しいのはその逆で、「**身内で、自分たちが決めたルールで、チップだけで**」遊ぶための道具である。

特に「カードの強さや役そのものを定義できる」ツールは事実上存在しない。ここが Wildcard の存在理由であり、
名前の由来（ワイルドカード = 規格外の札）でもある。

## 独自性 — ルールが設定データであること

通常のポーカー実装は役の強さをコードに焼き込む。Wildcard は**ルール定義を入力データとして受け取る**。

- スートの有効/無効、スート間の強さ順
- ランクの強さ順の差し替え
- 標準役（ロイヤルフラッシュ〜ハイカード）の有効/無効と優先順位の入れ替え
- カスタム役の追加 — 「変数ランク」で条件を書ける（例: `X, X, Y, Y+1, Y+2` でスート同一）

この「カスタム役を条件式で定義する」モデルは旧 poker-web-20250702 で設計済みであり、Wildcard はそれを引き継ぐ。

## やらないこと（明示的なスコープ外）

- リアルマネー、換金、賭博性のある運用
- 不特定多数のマッチメイキング / ランキング
- 大規模同時接続を前提とした設計
- 初期段階での常時稼働サーバー（コストを理由に意図的に避ける）

## 3つの試作から確定した要件

| 旧プロジェクト | そこで分かったこと | Wildcard への反映 |
|---|---|---|
| `poker-web-test` | ゲーム進行の正しさが一番難しい。席順、ブラインド位置、プリフロップ開始位置、ハンド途中参加、離席と自動フォールド | エンジンを通信から切り離し、進行ルールを単体テストできる形にする |
| `poker-web-20250702` | 遊ぶ以外の部分（クラブ、イベント、チップ付与、ハウスルール）が実は本体。中でもハウスルールが唯一の独自性 | ルール定義を中核に置く。クラブ/イベントは後段階 |
| `poker-web-20250702-game-ui` | 卓UIは重い状態管理より「席の配置」と「自分を手前に回す処理」が本質。1ファイルのバニラJSでも成立した | レイアウトとCSSを移植し、UIを薄く保つ |

## 配信の形

**サーバーを一切持たない。** GitHub Pages に静的配信するだけで、オンライン対戦まで
成立している。費用は永続的にかからない。

| モード | サーバー | どう成立しているか |
|---|---|---|
| ソロ（CPU相手） | 不要 | 同じタブの中でエンジンが回る |
| ホットシート | 不要 | 同じタブ。手番が移るたびに目隠しを挟む |
| オンライン対戦 | 不要 | 端末どうしが WebRTC で直接つながる |

### オンラインがサーバーなしで成立する理由

当初は「GitHub Pages は Node も WebSocket も動かせないので、オンライン対戦には
サーバーが要る」と見積もっていた。実際には、接続のきっかけ（SDP の交換）だけを
公開の WebTorrent トラッカー経由で済ませ、ゲームのデータは端末間を直接流す
ことで、サーバーなしで繋がる。トラッカーを通るのは接続情報だけで、
参加の瞬間にしか要らない。

この通信層は hayabuzz（同じ作者のサーバレスP2P早押しクイズ）の実装を
TypeScript に移植したもの。NAT越えとシグナリングという、自前でやると
一番ハマる部分が実戦で削れていた。

### その代わりに生じた前提

サーバーがない以上、**誰かの端末が配る役（host）になる**。その端末は全員の
ホールカードを計算できる立場にある。物理のホームゲームで誰かがシャッフルして
配るのと同じ構造で、暗号を使わない限り避けられない。

隠さずに画面へ出したうえで、配牌の操作（配り直し・seed 漁り）のほうは
全員が後から検証できるようにしてある。詳細は [fairness.md](./fairness.md)。

### この先

常時稼働のサーバーを立てる段階は、実際に遊んでみて必要になってから考える。
`Transport` を差し替えるだけで足せるので、今から備える必要はない
（詳細は [architecture.md](./architecture.md) の原則3）。
